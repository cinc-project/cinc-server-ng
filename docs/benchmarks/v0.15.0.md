# Performance benchmarks — cinc-server-ng v0.15.0 vs Chef Infra Server and chef-zero

Captured 2026-10-12 by the
[`benchmark-vs-chef-server`](../../.github/workflows/benchmark-vs-chef-server.yml)
workflow, [run 38306849072](https://github.com/cinc-project/cinc-server-ng/actions/runs/38306849072),
at commit `b2304ee` (v0.15.0 plus benchmark tooling; no server code changed
since the tag). Raw output for every run: [`v0.15.0-raw/`](v0.15.0-raw/).

**Every number in this report comes from the same machine**: one GitHub-hosted
`ubuntu-24.04` runner (x86_64, 4 cores), running Chef Infra Server (Cinc Server
15.10.125), chef-zero 15.1.11 and cinc-server-ng with the same load generator,
the same seeded data and, where a server verifies signatures, the same signing
identity. Earlier reports compared numbers taken on different machines; this
one replaces them.

## Method

- **One server at a time.** Only the server being measured is running: Chef
  Infra Server is stopped while the others run, so nothing competes for the
  runner's cores. Each cinc-server-ng and chef-zero run starts a fresh process.
- **Three runs per server, rotating order**, so no server always goes first or
  last. Every cell below is the **median** of the three
  ([`cmd/benchreport`](../../cmd/benchreport)).
- **Load:** [`cmd/loadtest`](../../cmd/loadtest), one organization seeded with
  500 nodes. Per operation: **cold ms** (first request on a fresh connection),
  **p50 / p95 ms** and **QPS@1** over 1000 sequential requests on one
  kept-alive connection, **QPS@10** at concurrency 10 for 3 s. Only 2xx
  responses are timed; all 15 runs completed with **zero failed requests**.
- **Memory:** [`scripts/memsample.sh`](../../scripts/memsample.sh) samples
  PSS summed over the server's whole process tree every 0.5 s: **idle** once
  the server is up and settled, **peak** while it is seeded and under load. PSS
  rather than RSS because Chef Infra Server's processes share pages, which RSS
  would count once per process.
- **Pairs to compare:** cinc-server-ng (SQLite) against Chef Infra Server, since
  both persist every write; cinc-server-ng (no auth) against chef-zero, since
  neither verifies signatures. Chef Infra Server is measured as it ships, nginx
  included, over HTTPS; cinc-server-ng and chef-zero over plain HTTP.

The workflow reruns all of this on demand: `gh workflow run benchmark-vs-chef-server.yml`.

## What it shows

**Against Chef Infra Server, both durable** (cinc-server-ng on SQLite):

| | GET node | GET node list | PUT node | search \*:\* | search filtered |
|---|--:|--:|--:|--:|--:|
| QPS@10 | 34× | 18× | 37× | 8× | 6× |
| QPS@1 | 104× | 65× | 107× | 10× | 6× |

It does this in **37 MiB at peak against Chef Infra Server's 5.2 GiB at
idle**: about 1/140 of the memory. Almost all of Chef Infra Server's footprint
is fixed cost (OpenSearch's preallocated Java heap and PostgreSQL), present
before the first request; load adds under 200 MiB. Search is where the gap is
smallest, the operation Chef Infra Server's architecture is built around.

**Against chef-zero, both unsigned** (cinc-server-ng without auth):

| | GET node | GET node list | PUT node | search \*:\* | search filtered |
|---|--:|--:|--:|--:|--:|
| QPS@10 | 133× | 74× | 52× | 148× | 161× |
| QPS@1 | 255× | 156× | 185× | 67× | 61× |

chef-zero's memory triples under load (44 to 143 MiB). cinc-server-ng stays
under 40 MiB in every mode, durable and authenticated included.

### The 45 ms floor

Chef Infra Server and chef-zero share the same latency floor on this machine:
45.0 ms p50 for a single-node GET on both, QPS@1 of 22 on both, and throughput
that scales almost exactly 10× from one connection to ten. Two unrelated server
stacks agreeing to the millisecond means the floor is not either server's work.
It matches Linux's ~40 ms delayed ACK meeting Nagle's algorithm when a server
writes a response in more than one segment without `TCP_NODELAY`; chef-zero
shows no such floor on macOS (1.4 ms p50 on an M4 Pro). Go's `net/http` sets
`TCP_NODELAY`, so cinc-server-ng is unaffected.

It is still what a client of either server sees on Linux, so it stays in the
results. It weighs most on sequential clients, such as a chef-client run making
its requests one after another, which is the QPS@1 and p50 columns; concurrency
hides it, which is why the QPS@10 ratios are smaller.

## Go benchmarks, v0.15.0 vs this commit

The workflow's `go-bench` job runs the fleet, search-scale, registration and
store benchmarks for the latest release and for the commit under test on the
same VM, interleaved, n=6 each
([`go-benchstat.txt`](v0.15.0-raw/go-benchstat.txt)). This commit changes no
server code, so the expected result is no change, and that is the result:
every benchmark is within noise except broad search at 512 and 2048 nodes, which
benchstat marks about 2% slower. With no search change in the diff, take that
as the noise floor of a shared VM: a smaller difference than about 2% is not
something this job can detect.

Absolute figures on this runner, for scale (HEAD medians):

| benchmark | runner |
|---|--:|
| enforced check-in, group-granted ACL, 2048 nodes | 34.7 µs |
| enforced check-in, SQLite | 75.8 µs |
| selective search, 8192 nodes | 62.1 µs |
| broad search (all match), 8192 nodes | 11.9 ms |
| register 8000 clients | 7.95 ms |

These are 2 to 4 times the M4 Pro figures in earlier reports. One difference
in kind: on 4 cores, SQLite group commit makes a single fleet check-in slower
(93.2 µs against 75.8 µs without it), where on 14 cores it was slightly faster.
Group commit trades latency on one serialized write for throughput across many
concurrent ones, and fewer cores leave less to batch.

## Caveats

- **Not like for like in what they do.** Chef Infra Server implements a great
  deal that cinc-server-ng does not. This measures what each gives you on one
  machine, the question when choosing a server for a test pipeline or a small
  fleet; it says nothing about Chef Infra Server on hardware sized for it.
- **HTTPS against plain HTTP.** Chef Infra Server is reached through its nginx
  front end over TLS.
- **Chef Infra Server keeps its data between runs**, so its second and third
  runs update the 500 nodes where every other server's runs create them.
- **A shared, virtualized runner.** Medians of three absorb a noisy run, not a
  noisy machine; the Go job's ~2% false positive is a fair guide to the noise
  floor.
- Search numbers depend on dataset size (500 nodes).
