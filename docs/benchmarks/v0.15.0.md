# Performance benchmarks — cinc-server-ng v0.15.0 vs chef-zero and Chef Infra Server

Captured 2026-10-12 at commit `76840cc` (`v0.15.0-6-g76840cc`: v0.15.0 plus
six fixes, none of them on a hot path). Three measurements, each reproducible:

| comparison | harness | where | raw output |
|---|---|---|---|
| vs **chef-zero** 15.1.11 | [`scripts/benchmark.sh`](../../scripts/benchmark.sh) (HTTP loadtest) | Apple M4 Pro, local | [`v0.15.0-raw.txt`](v0.15.0-raw.txt) |
| vs **Chef Infra Server** (Cinc Server 15.10.125) | [`benchmark-vs-chef-server.yml`](../../.github/workflows/benchmark-vs-chef-server.yml) | GitHub Actions, ubuntu-24.04 x86_64 | [`v0.15.0-chef-server-raw.txt`](v0.15.0-chef-server-raw.txt) |
| engine and fleet scale | Go benchmarks, `-count 5` | Apple M4 Pro, local | [`v0.15.0-gobench.txt`](v0.15.0-gobench.txt) |

Absolute numbers are machine-specific; the **ratios** are the durable result.
The chef-zero and Chef Infra Server numbers come from different machines and are
not comparable with each other.

## Method

Both HTTP comparisons use [`cmd/loadtest`](../../cmd/loadtest): one organization
seeded with **500 nodes** (nested attributes, half `production` / half
`staging`), identical across servers. Per operation: **cold ms** (first request
on a fresh connection), **p50 / p95 ms** (3000 sequential requests on a
kept-alive connection), **QPS@1** (one connection), **QPS@10** (concurrency 10).
In auth mode each operation is signed once and replayed, so QPS reflects
signature *verification* cost.

**chef-zero:** `seed=500 warm=3000 dur=3000ms conc=10`, loopback, the load
generator on the same host. Three full runs; each cell below is the **median of
the three**. (The first run's authenticated PUT and node-list figures were
about 4× and 3× low and did not reproduce in runs 2 and 3.) Darwin 27.0.0 arm64
· Apple M4 Pro (14 cores) · Go 1.27.1 · Ruby 4.0 · chef-zero 15.1.11 (WEBrick).

**Chef Infra Server:** one run, `seed=500 conc=10`, on a single hosted runner
that also runs both cinc-server-ng instances and the load generator. All three
servers are signed with the same user key, and all enforce ACLs.

### Speedup over chef-zero (no-auth)

| operation | p50 | QPS@10 |
|---|--:|--:|
| GET node | 34× | 112× |
| GET node list | 25× | 123× |
| PUT node | 23× | 53× |
| search \*:\* | 65× | 395× |
| search filtered | 78× | 379× |

chef-zero is single-process WEBrick: QPS@10 equals QPS@1, so it does not scale
with concurrency, and it re-flattens every node on every search. With signature
verification *and* ACL enforcement on, cinc-server-ng still serves 67–330× the
QPS@10 of a chef-zero that checks neither.

The authenticated `search filtered` cold figure (27.6 ms; 7.7 to 31.9 ms
across runs) is the first filtered query building its index and then
ACL-checking each result. It is a one-time cost per process.

**Compare the SQLite row against Chef.** Both persist every write. On QPS@10,
durable cinc-server-ng is **33× Chef on single-object reads and writes, 18× on
node lists, and 4–6× on search**. Search is where the gap is smallest: that is
the operation Chef Infra Server's architecture (OpenSearch) is built for.

### Chef's per-request latency is probably not erchef's

Treat Chef's p50 column with suspicion. Every simple operation sits on a flat
46–55 ms floor, which is *slower* than Chef's own filtered search (20 ms). A
single-node GET cannot cost more than a search over 500 nodes. Three more tells:

- QPS scales almost exactly 10× from concurrency 1 to 10 (22 → 209). The
  requests are waiting, not working.
- `GET node list` cold, on a fresh connection, took 13 ms, against a 49 ms p50
  on a reused one. A kept-alive connection should never be slower than a new one.
- A fixed ~40 ms stall on a reused connection is the signature of Nagle's
  algorithm meeting delayed ACKs. The Go client sets `TCP_NODELAY`, so if this is
  what is happening it is inside Chef's stack: the nginx front end, or erchef's
  per-request calls to bifrost.

So the latency ratio (~100× on a GET) probably overstates the gap, and the
QPS@10 ratio is the better number. Pinning this down would need a
diagnostic run that varies keep-alive on the client and on nginx's upstream.

### The comparison is not like for like

Every remaining difference favours cinc-server-ng:

- Chef Infra Server is erchef, PostgreSQL, OpenSearch, bifrost, bookshelf and
  nginx, sharing one hosted runner with both cinc-server-ng instances and the
  load generator.
- Chef is reached over HTTPS through nginx; cinc-server-ng over plain HTTP with
  no proxy.
- SQLite is an in-process file. PostgreSQL is a separate server with a wire
  protocol, and OpenSearch indexes every write.
- Chef implements a great deal that cinc-server-ng does not.

What this measures is what each server gives you on one machine, which is the
question that matters when choosing a server for a test pipeline. It says
nothing about Chef Infra Server on hardware sized for it.

## Engine and fleet scale (Go benchmarks)

Medians of five runs ([`v0.15.0-gobench.txt`](v0.15.0-gobench.txt)). The
v0.10.0 column is taken from [`v0.10.0.md`](v0.10.0.md) and was captured on the
same hardware model under Go 1.26.5 and Darwin 25.5. It is a cross-release
reference, not a same-session benchstat A/B, so read only large changes as real.

### Fleet behaviour

| benchmark | v0.10.0 | v0.15.0 |
|---|--:|--:|
| enforced check-in, group-granted ACL, 128 nodes | 11.22 µs | 11.22 µs |
| enforced check-in, group-granted ACL, 2048 nodes | 7.89 µs | 8.68 µs |
| register 500 clients | 0.43 ms | 0.20 ms |
| register 2000 clients | 1.45 ms | 0.81 ms |
| register 8000 clients | 4.69 ms | 3.36 ms |
| selective search, 512 nodes | 32.2 µs | 31.6 µs |
| selective search, 8192 nodes | 32.2 µs | 30.9 µs |
| broad search (all match), 512 nodes | 434.0 µs | 301.3 µs |
| broad search (all match), 8192 nodes | 6.78 ms | 4.83 ms |

v0.10.0's main result still holds: check-in and selective search cost the same
at 128 nodes as at 8192, and registration stays linear. Two regressions v0.10.0
reported have since improved. Broad searches matching every node, which became
slower in v0.10.0 when search started enforcing read ACLs, are ~30% faster
again. Fleet registration is 1.4–2.2× faster.

## Caveats

- WEBrick struggles past low concurrency. The chef-zero comparison is pinned at
  `conc=10` so chef-zero stays responsive; do not read its QPS@10 as a ceiling.
- Loopback, single host: the load generator competes for CPU. Cold figures are
  single samples and noisy.
- The Chef Infra Server comparison is a single run on a shared, virtualized
  runner. Rerun it with `gh workflow run benchmark-vs-chef-server.yml`.
- Search numbers depend on dataset size (500 nodes in the HTTP runs).
