# Performance benchmarks — cinc-zero v0.10.0 vs v0.9.0

Captured 2026-08-01. v0.9.0 is `b3f9c9d`, v0.10.0 is `f8160c4`.

**Environment:** Apple M4 Pro (14 cores) · Darwin 25.5.0 arm64 · Go 1.26.5.
Absolute numbers are machine-specific; the **ratios and the shape of the curves**
are the durable result.

## Method, and why it is not the usual one

Earlier reports used the HTTP loadtest in [`scripts/benchmark.sh`](../../scripts/benchmark.sh).
That harness runs `--no-auth` against a single organization, which is exactly
the configuration this release did not change — so it would report "no
difference" for a release whose work is all in authorization, search, and
registration at fleet scale.

Instead this compares Go benchmarks, run **on both versions**. The benchmarks
that measure fleet behaviour were written during this release, so they were
copied into a v0.9.0 worktree and run against the old implementation. Only one
line needed adapting (`actorGroups` became a method); everything else compiled
unchanged, so both columns are the same measurement of different code.

`benchstat`, n=5. Raw output: [`v0.10.0-raw.txt`](v0.10.0-raw.txt).

## Fleet check-in, ACL enforcement on

One signed request through the whole stack — Mixlib verification, API version
negotiation, ACL enforcement, store — with the node's ACL granting through a
group, which is the shape Chef's default ACLs have.

| fleet size | v0.9.0 | v0.10.0 | change |
|---|--:|--:|--:|
| 128 nodes | 29.72 µs | 11.22 µs | **−62%** |
| 512 nodes | 52.54 µs | 9.25 µs | **−82%** |
| 2048 nodes | 134.18 µs | 7.89 µs | **−94%** |

The percentages understate it. In v0.9.0 the cost **grew with the size of the
fleet** — resolving one actor's group membership scanned and decoded every group
in the organization, and the org's `clients` group holds one entry per node. In
v0.10.0 it is flat: 128 nodes and 2048 nodes cost the same.

## Registering a fleet

Standing up N clients, each joining the organization's `clients` group and then
resolving its own membership on first authenticated request.

| fleet size | v0.9.0 | v0.10.0 | change |
|---|--:|--:|--:|
| 500 clients | 41.0 ms | 0.43 ms | **−99.0%** |
| 2000 clients | 637.7 ms | 1.45 ms | **−99.8%** |
| 8000 clients | 10.14 s | 4.69 ms | **−99.95%** |

v0.9.0 was quadratic: membership lived in a single document per group, so each
registration rewrote a document containing every member already registered.
16× the nodes cost 247× the time. v0.10.0 is linear.

## Search

Selective query — one node matched out of the fleet:

| collection | v0.9.0 | v0.10.0 | change |
|---|--:|--:|--:|
| 512 nodes | 86.8 µs | 32.2 µs | **−63%** |
| 2048 nodes | 262.0 µs | 31.7 µs | **−88%** |
| 8192 nodes | 1295.1 µs | 32.2 µs | **−97.5%** |

Flat, again: a query matching one document costs the same whether the collection
holds 512 or 8192, where before it cost a full scan every time.

Broad query — every node matched:

| collection | v0.9.0 | v0.10.0 | change |
|---|--:|--:|--:|
| 512 nodes | 695.6 µs | 434.0 µs | −38% |
| 2048 nodes | 1.63 ms | 1.70 ms | +5% |
| 8192 nodes | 4.42 ms | 6.78 ms | **+53%** |

**This one is slower, and the comparison is not like-for-like.** v0.9.0 did not
filter search results by ACL at all — it returned every matching document to any
authenticated caller. v0.10.0 checks each row against the requester's read
permission. On a query that matches everything, that filtering costs more than
the index saves. The v0.9.0 number is the speed of not doing the work.

## SQLite writes, default configuration

Group commit became the default in v0.10.0, so this is what a durable
deployment gets without changing any flags. Sustained 16-writer load, 6400
writes, median of 3 runs.

| | v0.9.0 default | v0.10.0 default | change |
|---|--:|--:|--:|
| throughput | 40,388 writes/s | 81,997 writes/s | **+103%** |
| p50 | 164 µs | 119 µs | −27% |
| **p99** | **3.32 ms** | **0.44 ms** | **−87%** |
| max | 13.2 ms | 7.2 ms | −45% |

The p99 is the number that matters for a server absorbing check-ins: the tail is
where a converge stalls, and a mean hides it.

## Unchanged

Neither better nor worse, within noise:

| | v0.9.0 | v0.10.0 |
|---|--:|--:|
| enforced check-in, ACL naming the actor directly | 9.16 µs | 9.38 µs |
| authenticated check-in, no ACL enforcement | 7.53 µs | 7.55 µs |
| in-memory check-in (`BenchmarkCheckinsMemory`) | 7.92 µs | 8.00 µs |
| SQLite check-in (`BenchmarkCheckinsSQLite`) | 32.68 µs | 33.68 µs |
| RSA signature verification | ~6 µs | ~6 µs |
| server startup, 1 org | 57.7 ms | 62.3 ms |

## Regressions

Reported because they are real, and small:

| | v0.9.0 | v0.10.0 | change |
|---|--:|--:|--:|
| unauthenticated check-in | 3.245 µs | 3.396 µs | +4.7% |
| `BenchmarkListObjects` | 42.75 µs | 45.74 µs | +7.0% |
| `BenchmarkSearchScanWarm` | 32.37 µs | 34.43 µs | +6.4% |
| SQLite `Get` | 4.350 µs | 4.726 µs | +8.7% |

These come from bookkeeping the release added: the store counts its operations
so `/_stats` can report read amplification, and reports each committed write so
the search and membership indexes can stay current. It is a fixed cost per
operation, paid by paths that do not benefit from the indexes it maintains.

## Summary

The release does not make a single request meaningfully faster. It removes the
two places where cost **grew with the size of the fleet** — group membership
resolution on every authorized request, and membership writes on every
registration — and makes selective search independent of collection size. On a
2048-node fleet that is 17× on check-in; on an 8000-node bootstrap it is
2160×; at 8192 documents a selective search is 40× faster.

Against that: broad searches that match most of a collection are slower, because
they now enforce read ACLs that v0.9.0 did not enforce at all.
