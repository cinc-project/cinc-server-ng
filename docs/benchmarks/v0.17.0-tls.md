# TLS cost: cinc-server-ng v0.17.0, HTTP vs HTTPS

What serving TLS natively (`--tls-cert` / `--tls-key`, new in 0.17) costs,
measured against the same binary over plain HTTP. Raw output for every run:
[`v0.17.0-tls-raw/`](v0.17.0-tls-raw/).

Captured 2026-10-13 on one machine: Apple M4 Pro (14 cores, 24 GiB), macOS
27.0.1, Go 1.27.1, from branch `feat/tls-and-load-balancer` on top of
`6342085`. Client and server share the machine and talk over loopback. That
isolates the protocol cost from the network, but it also means **the client's
TLS work competes with the server's for the same cores**, so the throughput
gaps below are an upper bound on what the server alone pays.

A first collection was discarded because Spotlight indexing held the load
average near 40 and made the Go benchmarks swing 4×. This one started at a
load average of 4.3. The benchmark itself raised it to about 13 (the server
plus ten load-generator workers), which affects both transports equally since
they alternate.

## Method

- **End to end** ([`scripts/bench-tls.sh`](../../scripts/bench-tls.sh)):
  [`cmd/loadtest`](../../cmd/loadtest) against the `cinc-server-ng` binary,
  in-memory backend, authentication and ACL enforcement on (the binary's
  defaults), one organization seeded with 500 nodes, every request signed.
  The HTTPS run uses a P-256 self-signed certificate (what an ACME client
  issues by default) with TLS 1.3 and HTTP/1.1 keep-alive. **Five runs per
  transport, alternating order**, each on a fresh process. Every cell is the
  median of the five ([`cmd/benchreport`](../../cmd/benchreport)). All ten runs
  completed with **zero failed requests**.
- **In process** (`server/tls_bench_test.go`, `go test -bench Transport`): a
  signed GET of one node through the whole server stack, 14 parallel clients,
  either on kept-alive connections (`Reuse`) or with a new connection, and so a
  full handshake, per request (`NewConn`). `-count 10`, compared with
  benchstat.

Reproduce with `REPS=5 scripts/bench-tls.sh <dir>` and
`go test ./server/ -run '^$' -bench Transport -count 10`.

## Reading the numbers

- **Small requests on a kept-alive connection cost about the same over TLS.**
  A single-node GET is within noise in process and 4% slower end to end.
  Symmetric encryption of a few kilobytes is cheap next to signature
  verification and JSON handling.
- **The cost grows with response size.** Node lists and `search *:*` return
  all 500 nodes, and they lose 15–21% of their concurrent throughput, since
  both ends encrypt and decrypt every byte on the same cores.
  Single-connection throughput, where the cores are not saturated, loses
  2–14%.
- **The handshake is the expensive part:** about 1.5–2.5 ms on the first
  request of a connection, and 3× the per-request cost (5× the memory) when
  nothing is reused. chef-client and knife keep a connection open for a run,
  and load balancers pool backend connections, so in practice the handshake
  is paid rarely. Configurations that defeat reuse (`Connection: close`,
  very short idle timeouts) are where TLS shows up.
- **On a 4-core Linux runner** the cost is smaller: 2–12% of QPS@10, least
  on SQLite and search, measured against Chef Infra Server and chef-zero in
  the [v0.17.0 report](v0.17.0.md).
- **Native TLS against a proxy in front:** a TLS-terminating proxy pays the
  same cryptography plus an extra hop and copy, so these numbers also bound
  what moving TLS from nginx into cinc-server-ng can cost. For scale, Chef
  Infra Server measured on its nginx front end over HTTPS in the
  [v0.15.0 report](v0.15.0.md) served 210 QPS@10 for a single-node GET,
  on different hardware.
