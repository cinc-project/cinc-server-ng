# Performance benchmarks — cinc-server-ng v0.17.0 vs Chef Infra Server and chef-zero

Captured 2026-10-13 by the
[`benchmark-vs-chef-server`](../../.github/workflows/benchmark-vs-chef-server.yml)
workflow, [run 38368711990](https://github.com/cinc-project/cinc-server-ng/actions/runs/38368711990),
at commit `8ebece4` (the native TLS work for 0.17). Raw output for every run:
[`v0.17.0-raw/`](v0.17.0-raw/).

**New in this report: cinc-server-ng over HTTPS.** Every earlier report
measured Chef Infra Server over HTTPS (through its bundled nginx) and
cinc-server-ng over plain HTTP, because cinc-server-ng could not serve TLS. It
now can (`--tls-cert` / `--tls-key`), so the durable-against-durable pair is
measured with TLS on both sides.

All numbers come from one GitHub-hosted `ubuntu-24.04` runner (AMD EPYC 9V74,
4 cores), running Chef Infra Server (Cinc Server), chef-zero 15.1.11 and
cinc-server-ng with the same load generator, the same seeded data and, where a
server verifies signatures, the same signing identity.

## Method

As in [v0.15.0](v0.15.0.md):

- **One server at a time**, each cinc-server-ng and chef-zero run on a fresh
  process, Chef Infra Server stopped while the others run.
- **Three runs per server, rotating order.** Every cell is the **median** of
  the three ([`cmd/benchreport`](../../cmd/benchreport)).
- **Load:** [`cmd/loadtest`](../../cmd/loadtest), one organization seeded with
  500 nodes. **cold ms** is the first request on a fresh connection (so over
  HTTPS it includes the handshake), **p50 / p95 ms** and **QPS@1** come from
  1000 sequential requests on one kept-alive connection, and **QPS@10** is
  concurrency 10 for 3 s. All 21 runs completed with **zero failed requests**.
- **Memory:** [`scripts/memsample.sh`](../../scripts/memsample.sh), PSS summed
  over each server's whole process tree, idle and peak under load.
- **HTTPS rows:** cinc-server-ng serving TLS itself with a self-signed P-256
  certificate (HTTP/1.1 keep-alive, as for every server). Chef Infra Server serves TLS
  through nginx with the certificate it generates at install. chef-zero stays
  on plain HTTP: its `--ssl` mode generates a certificate without a
  subjectAltName, which Go clients reject.

## What it shows

**Against Chef Infra Server, both durable, both over HTTPS** (cinc-server-ng on
SQLite with native TLS):

| | GET node | GET node list | PUT node | search \*:\* | search filtered |
|---|--:|--:|--:|--:|--:|
| QPS@10 | 33× | 17× | 34× | 8× | 5× |
| QPS@1 | 101× | 66× | 101× | 10× | 6× |

Over plain HTTP, the comparison earlier reports made, the same pair gives
34×, 19×, 36×, 8× and 6× at QPS@10, so TLS barely moves the result. It does
this in **39 MiB at peak against Chef Infra Server's 5.2 GiB at idle**.

**What TLS costs cinc-server-ng on this runner** (HTTPS against HTTP, same
backend):

| | GET node | GET node list | PUT node | search \*:\* | search filtered |
|---|--:|--:|--:|--:|--:|
| SQLite, QPS@10 | −3.9% | −9.4% | −4.7% | −2.2% | −1.8% |
| in memory, QPS@10 | −7.7% | −12.0% | −7.4% | −4.9% | −4.6% |
| SQLite, QPS@1 | −2.3% | −3.8% | −2.2% | −3.8% | −0.8% |
| in memory, QPS@1 | −5.0% | −8.8% | −4.4% | −4.4% | −0.4% |

The cost is largest where requests are cheapest and responses biggest (the
node list returns all 500 nodes), and smallest where per-request work
dominates: search and the SQLite backend. A new connection costs about 1 ms
more cold (the handshake). Memory grows by 1–2 MiB. Single-run differences of
a few percent are near this runner's noise floor (see below), so read the
pattern rather than any one cell. On an M4 Pro over loopback, where the
load generator's own TLS work competes for the same cores, large responses
lost up to 21%; see [`v0.17.0-tls.md`](v0.17.0-tls.md).

**Against chef-zero, both unsigned and on plain HTTP** (cinc-server-ng without
auth):

| | GET node | GET node list | PUT node | search \*:\* | search filtered |
|---|--:|--:|--:|--:|--:|
| QPS@10 | 133× | 76× | 51× | 160× | 178× |
| QPS@1 | 253× | 155× | 178× | 69× | 67× |

The 45 ms latency floor that Chef Infra Server and chef-zero share on Linux
(delayed ACK meeting Nagle's algorithm, explained in the
[v0.15.0 report](v0.15.0.md#the-45-ms-floor)) is still there and still
decides their sequential numbers. cinc-server-ng is unaffected over HTTPS as
well as over HTTP.

## Go benchmarks, v0.16.0 vs this commit

The `go-bench` job runs the fleet, search-scale, registration and store
benchmarks for v0.16.0 and for this commit on the same VM, interleaved, n=6
each ([`go-benchstat.txt`](v0.17.0-raw/go-benchstat.txt)). TLS is off unless
configured, and none of these benchmarks configure it, so the expected
result is no change on the request path, and that is the result. Fleet
check-ins, registration, list and the store's Get/Put are within noise. Search at
8192 nodes (broad 4%, selective 1%) and the enforced SQLite check-in (2%) are
marked faster; nothing on either path changed since v0.16.0, so like v0.15.0's 2%
false positives they mark this runner's noise floor, not an improvement.

One result looks alarming and isn't: `WriteLatency` (SQLite without group
commit) reports writes/s −63% and p99 +482%, both marked significant. The
store code is identical between v0.16.0 and this commit. The benchmark runs
one fixed workload regardless of `b.N` and is meant to be run with
`-benchtime 1x`, but the workflow runs it with the default benchtime, so the
framework's ramp-up calls it a varying number of times. Three of the six
v0.16.0 samples came from a run that ramped to `b.N = 1e9` (and report 0 B/op),
and those three are exactly the fast ones. Until the workflow runs this
benchmark at `-benchtime 1x`, its samples are not comparable across runs.

Absolute figures on this runner, for scale (HEAD medians):

| benchmark | runner |
|---|--:|
| enforced check-in, group-granted ACL, 2048 nodes | 28.3 µs |
| enforced check-in, SQLite | 59.6 µs |
| selective search, 8192 nodes | 48.5 µs |
| broad search (all match), 8192 nodes | 8.79 ms |
| register 8000 clients | 6.09 ms |

## Caveats

- **Not like for like in what they do.** Chef Infra Server implements a great
  deal that cinc-server-ng does not. This measures what each gives you on one
  machine; it says nothing about Chef Infra Server on hardware sized for it.
- **TLS setups differ in detail.** cinc-server-ng serves a self-signed P-256
  certificate natively; Chef Infra Server serves its generated certificate
  through nginx. Both are measured with the same Go client.
- **Chef Infra Server keeps its data between runs**, so its second and third
  runs update the 500 nodes where every other server's runs create them.
- **A shared, virtualized runner.** Medians of three absorb a noisy run, not a
  noisy machine. Differences of a few percent between rows from different
  runs are near the noise floor.
- Search numbers depend on dataset size (500 nodes).
